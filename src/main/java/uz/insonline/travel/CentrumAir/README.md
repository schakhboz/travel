# Модуль выпуска Centrum Air

Реализация ТЗ «Встроенное страхование пассажиров Centrum Air», v3.0.

## Эндпоинты

| Метод  | Путь                             | Назначение                                        |
|--------|----------------------------------|---------------------------------------------------|
| POST   | `/policy/issue`                  | Выпуск полисов по брони (идемпотентный)           |
| DELETE | `/policy/cancel`                 | Аннуляция полиса при возврате билета               |
| GET    | `/policies` (и `/policy/policies`) | Журнал полисов: период, продукт, статус          |
| GET    | `/centrum-air/dictionary/tariffs` | Тарифная матрица: ставки по продуктам и типам маршрута |
| GET    | `/centrum-air/dictionary/risks`  | Реестр рисков: классы и страховые суммы            |
| POST   | `/calculator`                    | Расчёт премии с расшифровкой, без выпуска          |

`/policy/policies` оставлен как алиас, чтобы не ломать текущую интеграцию; ТЗ требует `/policies`.

## Идемпотентность (ТЗ п. 7.3)

Ключ:
* заголовок `Idempotency-Key`, если он передан;
* иначе — `SHA-256(PNR | набор продуктов | идентификаторы транзакций а/к)`. Транзакции уже есть
  в запросе и уникальны для платежа: повтор того же запроса даёт тот же ключ, новая оплата той же
  брони — новый. Если блок `transactions` пуст, вместо него берётся `paymentTime`.
  Новых полей в контракте API нет.

Поведение повтора:

| Состояние заявки | Что делает повтор |
|------------------|-------------------|
| `COMPLETED`      | возвращает сохранённый ответ первичного выпуска, ничего не выпуская |
| `PARTIAL` / `FAILED` | довыпускает только недостающие учётные группы |
| `IN_PROGRESS` (свежая) | `409 issue_in_progress` |
| `IN_PROGRESS` (старше `idempotency.in-progress-timeout`) | перехватывает зависший выпуск |
| тот же ключ, другое тело | `422 idempotency_key_reuse` |
| без заголовка, активная заявка на ту же бронь и продукты | `409 duplicate` (ТЗ п. 7.6.5) |

Каждая учётная группа выпускается в собственной транзакции (`PolicyGroupIssuer`), поэтому сбой на
третьем полисе не откатывает первые два, а факт выпуска сразу пишется в
`INS_CENTRUM_AIR_IDEMP_POLICY`.

Таблицы создаются скриптом `src/main/resources/db/centrum_air_idempotency.sql` (Oracle 11g;
`ddl-auto: validate` — DDL приложением не создаётся).

## Калькулятор для партнёров

`POST /calculator` показывает, как складывается премия: параметры поездки без персональных данных
на входе, на выходе — состав полисов, слагаемые премии каждого полиса (тарифная ставка, множитель,
формула) и доля каждого риска с его страховой суммой. Ничего не сохраняется и не выпускается.

```json
{
  "routeType": "RT", "isInternational": true, "isSchengen": false,
  "passengerCount": 2,
  "departureDate": "2026-09-04", "returnDate": "2026-09-15",
  "products": [{"productCode": "MAXIMUM"}, {"productCode": "ADDON_BAGGAGE", "quantity": 2}]
}
```

Арифметика — та же, что в `POST /policy/issue`: обе ветки читают одну тарифную матрицу и делят
премию по рискам одним методом `PolicyCalculationService.splitPremiumByRisk`. Правила совместимости
продуктов вынесены в `ProductRules` и действуют одинаково при выпуске и в калькуляторе, поэтому
партнёр видит те же отказы, что получит при выпуске. Совпадение сумм закреплено тестом
`PremiumCalculatorServiceTest`: если формулы разъедутся, сборка упадёт.

## Структура

```
config/      настройки модуля (продукт, курс, имена функций НАПП, пороги валидации)
dictionary/  справочники тарифов и рисков, калькулятор премии для партнёров
domain/      ProductSelection, RiskCatalog, ProductRules, Kontragent — правила без БД и Spring
error/       коды ошибок ТЗ п. 7.6.6 и обработчик только для PolicyController
idempotency/ ключи, состояние заявки, довыпуск
jdbc/        весь прямой SQL и вызовы пакета ERSP_VOLUNTARY_INTEGRATIONS
service/     сценарии: валидация, расчёт, выпуск группы, оркестрация, журнал, аннуляция
```

## Сертификат и письмо пассажиру

После выпуска всех полисов брони модуль публикует заявку в обменник
`insurance.certificate.exchange` (ключ `insurance.certificate.issue`) и сразу отвечает
авиакомпании. PDF-сертификат, его хранение в MinIO и письмо пассажиру — **отдельный сервис**
(`inson-certificate-service`, свой репозиторий): здесь остаётся только публикация.

Единственная связь — сообщение `CertificateRequestMessage`. Его копия живёт и в сервисе
документов; обе стороны сериализуют одинаковый JSON, поэтому имена пакетов расходиться могут,
а поля — нет. Обменник объявляется здесь, очередь, привязку и DLQ создаёт сервис документов.
Сбой публикации не отменяет выпущенные полисы — он только логируется.

## Что осталось за рамками (ТЗ, но не реализовано)

* `PUT /policy/update` и `POST /policy/resend` — методы ТЗ п. 8.1;
* электронный полис ЕАИС (PDF, ТЗ п. 9.1) — формирует НАПП;
* повторная отправка документов пассажиру: сервис сертификатов умеет её по флагу `resend`
  в сообщении, HTTP-метод `POST /policy/resend` здесь не опубликован;
* ретраи при недоступности НАПП до 24 часов и статус «Ошибка выпуска» с алертом — ТЗ п. 7.4;
  сейчас неуспешная группа остаётся недовыпущенной до повторного запроса а/к;
* курс EUR берётся из конфигурации, а не из справочника курсов на дату выпуска — ТЗ п. 3.1;
* сверка премии с тарифной матрицей выключена (`validation.check-premium: false`) до согласования
  разбивки премии по рискам — ТЗ п. 13.
